# `services/db` — persistencia F1

Camino **no destructivo** desde la SQLite actual a un Postgres de desarrollo.
Nunca se abre ni se escribe en `data/qvaapply.sqlite`:

1. Se copia el fichero a `/tmp` y se verifica su `sha256` antes y después.
2. La copia se migra a v31 con `tools/db-rehearsal/rehearse.mjs` (también sobre
   copia).
3. Se importa a una base Postgres **nueva** y un schema explícito (`core`).

## Postgres local aislado

```bash
docker compose -f services/db/compose.postgres.yaml up -d
```

- `127.0.0.1:55432`
- base `qvaapply`
- usuario `qvaapply`
- contraseña **solo de desarrollo**: `qvaapply_dev_only`
- volumen `qvaapply-f1-pgdata`

No usar estas credenciales fuera de desarrollo.

## Importar una copia v31

```bash
# 1) Copia de trabajo + migración v16→v31 (nunca toca el original)
node --import tsx tools/db-rehearsal/rehearse.mjs \
  --source /tmp/prod-copy/qvaapply.sqlite \
  --workdir /tmp/qva-f1-rehearsal \
  --json /tmp/qva-f1-rehearsal.json --keep

# 2) Importación raw→core al Postgres aislado
PGHOST=127.0.0.1 PGPORT=55432 PGUSER=qvaapply \
PGPASSWORD=qvaapply_dev_only \
node services/db/import-sqlite-to-postgres.mjs \
  --source /tmp/qva-f1-rehearsal/data/qvaapply.sqlite \
  --database qvaapply --schema core --replace \
  --manifest /tmp/qva-f1-import.json
```

El importador exige `--replace` para recrear un schema existente y verifica:

- conteos por tabla (SQLite vs Postgres);
- digest MD5 de `settings` con orden binario (`COLLATE "C"`);
- `sha256` del origen sin cambios;
- 41 tablas / **16 533 filas** en la copia de ensayo;
- 41 claves primarias, 40 índices y 6 claves foráneas.

## Esquema versionado y migraciones

`schema/core-v1.sql` es el snapshot `pg_dump --schema-only` del schema `core`
(41 tablas, PKs con identidad, índices y FKs). Se aplica a una base vacía con:

```bash
createdb qvaapply_f1
bash services/db/migrate.sh
```

`migrate.sh` aplica en orden los `migrations/*.sql`, registra cada versión en
`public.qvaapply_schema_migrations` y ejecuta migración + registro en una sola
transacción:

- `0001_core.sql` → snapshot del esquema.
- `0002_triggers.sql` → los 6 triggers de comportamiento.
- `0003_outbox_inbox.sql` → `outbox`, `inbox` e `idempotency_keys` con sus
  constraints e índices de pendientes.

Los triggers se aplican **después** de la carga inicial para no duplicar
histórico. Los 8 `id` autoincrementales llevan `GENERATED BY DEFAULT AS
IDENTITY` y sus secuencias se ajustan al máximo importado.

## Auditor de invariantes e importes

```bash
# Sobre cualquier base migrada
PGDATABASE=qvaapply bash services/db/audit-invariants.sh

# Compara saldos, ledger y operaciones entre una copia SQLite v31 y Postgres
PGDATABASE=qvaapply node services/db/verify-money.mjs --source /tmp/copy-v31.sqlite
```

El auditor comprueba, entre otras:

- reservas de aplicación huérfanas, terminales, confirmadas o no positivas;
- oferta con más de una reserva de aplicación y workflows duplicados;
- doble asiento de ledger, importes no positivos y saldos fiat negativos;
- tasas de mercado y límites de riesgo incoherentes;
- reserva QUSD no harmonizada y cadena de configuración/epoch rota.

`verify-money.mjs` compara los saldos `fiat_balance:*`, los agregados del ledger
por moneda/dirección y el count/suma de operaciones con 8 decimales.

## Outbox, inbox e idempotencia

La migración `0003` crea:

- `core.outbox` con clave de idempotencia única, estados y lease;
- `core.inbox` deduplicado por `(consumer, message_id)`;
- `core.idempotency_keys` por `(scope, key)` con hash de request y expiración.

El fixture `fixtures/outbox-inbox.sql` comprueba uniqueness, CHECKs y
transiciones; se ejecuta en `test-postgres.sh`.

## Verificación en CI

```bash
# esquema + triggers sobre base desechable
bash services/db/test-postgres.sh

# importación desde un fixture SQLite mínimo + triggers
bash services/db/test-postgres-import.sh
```

Ambos scripts crean una base única, ejecutan las comprobaciones y la borran.
El workflow `postgres-f1` los ejecuta contra `postgres:16`; el deploy depende de
ese job.

## Seguridad

- `--replace` es obligatorio para borrar un schema; no hay borrado implícito.
- El importador solo escribe en `--database`/`--schema` y usa `psql` con
  `ON_ERROR_STOP=1`.
- No se versionan dumps ni filas; solo estructura, conteos y digests agregados.
- `data/` permanece intacto: el `sha256` del fichero original se comprueba antes
  y después.
